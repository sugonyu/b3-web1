BookLoop

A privacy-conscious community for sharing Korean-language books in Montreal.

Definition and Design · MVP v0.1 · July 30, 2026 · Tony Yu

Deliverable 1 presentation baseline Version 1.0 · July 29, 2026

01 · Simulated client quote

Make scarce Korean books easier to share locally.

“Our Montreal community needs a simple way to discover and share Korean-language books without publicly exposing exact addresses or personal contact details.”

Client need

A searchable local directory and a controlled request workflow.

Product boundary

Show a general area publicly; connect members only after owner approval.

02 · Target user and problem

Useful books exist, but they are hard to discover safely.

Target user

Korean-speaking adults in Montreal who want to lend or borrow Korean books.

Problem

Local Korean books are scarce, while informal sharing depends on scattered personal contacts.

Privacy risk

Publishing email, phone number, or a precise address creates unnecessary exposure.

03 · Controlled scope

One complete workflow before extra features.

Must-have for the project

  • Member, book listing, and borrow-request data
  • BookListing CRUD
  • Borrow request creation and status changes
  • Owner information boundary and general area
  • Relational persistence and validation

Optional after the core works

  • Trust rating based on completed exchanges
  • Private notes about a book or request
  • Hide one listing or a member's full listing set
  • Realtime notifications

04 · Primary workflow

Discovery becomes a recorded, owner-approved exchange.

Browse booksView detailsRequest book Owner decidesLimited connectionReturn recorded

The BorrowRequest record turns a directory into a real application and creates the future foundation for trust history.

05 · Frontend track and backend

React client + Flask JSON API

React

A modern component-based client that can later connect to another backend such as Supabase.

Flask JSON API

A course-aligned Python backend with an explicit frontend/backend boundary.

SQLAlchemy + SQLite

A small relational foundation for models, foreign keys, CRUD, and persistence.

Authentication is designed here and implemented in Deliverable 2. The current private prototype uses temporary user IDs.

07 · Proposed data model

Three models support one complete exchange.

User

id, username, email, password_hash, general_area

BookListing

id, title, author, availability, owner_id

BorrowRequest

id, status, listing_id, borrower_id

User (owner)       1 ─────────── many BookListing
User (borrower)    1 ─────────── many BorrowRequest
BookListing        1 ─────────── many BorrowRequest

Public listing responses expose a username and general area, but not email, password data, phone number, or a precise address.

08 · Proposed endpoint contract

Seven endpoints cover CRUD and the request workflow.

#Method and pathPurposeBoundary
1GET /api/listingsBrowse listingsPublic
2POST /api/listingsCreate a listingAuthenticated
3GET /api/listings/:idView one listingPublic
4PATCH /api/listings/:idUpdate one listingOwner
5DELETE /api/listings/:idDelete one listingOwner
6POST /api/listings/:id/requestsCreate a borrow requestBorrower
