문서 버전 v1.7 · BookLoop Beta v0.4.0-beta.2

등급 이유: v1.6의 Flask 아키텍처와 LAN/SQLite 운영 지도를 유지하면서 Beta Report workflow와 사용자 책 관리 흐름을 추가했습니다. Report 제출자는 My reports에서 자신의 상태와 상세를 추적하고, Admin은 Received reports에서 신고자를 확인한 뒤 Open / Under review / Resolved / Dismissed 상태를 저장할 수 있습니다. Admin detail은 외부 연락용 email link를 제공하지만 자동 email과 moderation audit log는 Future Request로 남겨 두었습니다. 로그인 사용자는 My books에서 책을 등록·수정·availability 변경·삭제할 수 있고, request history가 있는 책은 기록 보존을 위해 삭제할 수 없습니다. DB Inspector는 Report row와 moderation details를 read-only로 보여주며 reporter/reported user의 email과 password hash는 표시하지 않습니다. 현재 제품 기준선은 BookLoop Beta v0.4.0-beta.2입니다.

이 번호는 Code Map 문서의 진화 기록이며, BookLoop 제품 MVP 버전이나 공식 Deliverable 번호를 뜻하지 않습니다. 이전 v1.6은 동결 보관본으로 유지합니다.

1.1 · create_app() 설정과 모듈 조립

전체 지도를 읽기 전에 bookloop/__init__.py의 application factory를 먼저 이해합니다. 각 파일은 자기 역할을 정의하고, create_app()이 설정·extension·Blueprint·개발 명령을 하나의 Flask 앱으로 조립합니다.

Fig 1.1-1 · Flask App 4대 Blueprint Core 제품 아키텍처 (4대 입구 ➔ Shared Services ➔ SQLite)

제품 아키텍처의 핵심은 "auth + jinja_client + admin + api" 4대 Blueprint 입구입니다. 각 입구는 자신의 포장 방식(HTML vs JSON vs 인증 세션)만 다를 뿐, 수렴하여 공통 Shared Services와 SQLAlchemy ORM을 재사용합니다.

Fig 1.1-3 · bookloop/__init__.py Application Factory 8단계 조립 코드 & 주석 명세

📄 bookloop/__init__.py · Application Factory 핵심 구현 코드 & 요점 주석 create_app(test_config=None) 
def create_app(test_config=None):
    # 1. [.env 환경변수 로드 & Flask 인스턴스 생성]
    load_dotenv()
    app = Flask(__name__, instance_relative_config=True)

    # 2. [기본 설정 매핑: DB URI, Secret Key, Dev DB Inspector/User Switcher 보안 옵션]
    app.config.from_mapping(
        SECRET_KEY=os.getenv("SECRET_KEY", "dev-only-change-me"),
        SQLALCHEMY_DATABASE_URI=os.getenv("DATABASE_URL", "sqlite:///bookloop.db"),
        SQLALCHEMY_TRACK_MODIFICATIONS=False,
        ENABLE_DEV_DB_INSPECTOR=...,  # 개발 전용 DB Inspector 허용 옵션
        ENABLE_DEV_USER_SWITCHER=..., # 데모 사용자 관점 전환 허용 옵션
    )

    # 3. [Flask Extensions 바인딩: SQLAlchemy ORM + Flask-Login]
    db.init_app(app)
    login_manager.init_app(app)

    # 4. [ORM Model Metadata 바인딩 (db.create_all 준비)]
    from .db import models  # User, BookListing, BorrowRequest 모델 메타데이터 등록

    # 5. [Cross-Origin CORS 허용: React dev server(:3000) & static(:8080) ➔ Flask API(:5000)]
    CORS(app, resources={r"/api/*": {"origins": ["http://localhost:3000", "http://localhost:8080"]}})

    # 6. [Blueprint 등록: 4대 핵심 입구 + Dev Tools]
    app.register_blueprint(api)              # 📤 JSON API (/api/...)
    app.register_blueprint(admin)            # 🛡️ Admin HTML (/admin/...)
    app.register_blueprint(auth)             # 🔐 Auth (login/logout/register)
    app.register_blueprint(jinja_client)     # 🐍 Jinja Product HTML
    app.register_blueprint(vanilla_client)   # 🟨 Flask Vanilla client
    app.register_blueprint(db_inspector)     # 🧪 Dev DB Inspector
    app.register_blueprint(user_switcher)    # 🧪 Dev User Switcher

    # 7. [Flask CLI Seed 명령어 바인딩: seed-demo, reset-demo-requests]
    register_seed_commands(app)

    # 8. [instance 폴더 보장 후 App 인스턴스 반환]
    os.makedirs(app.instance_path, exist_ok=True)
    return app

React SPA(:3000) & Static(:8080) CORS를 허용하고 4대 제품 Blueprint와 개발 도구를 등록합니다.

4 · CLI Seed & Instance 경로

register_seed_commands(app)로 CLI 명령을 등록하고 instance/ 폴더 생성을 보장 후 반환합니다.

핵심 구분: jinja_product.py나 api.py가 앱을 따로 실행하는 것이 아닙니다. 이 파일들은 Blueprint와 route를 정의하고, create_app()이 모두를 조립한 뒤 run.py가 서버를 시작합니다.

CLI는 Blueprint가 아닙니다: Blueprint는 HTTP route를 묶는 Flask 모듈이고, CLI는 터미널 명령입니다. 이 프로젝트의 seed/reset은 app.cli에 등록되는 Flask CLI 경로와, backend/bl_cli.py가 직접 실행하는 Click 경로로 제공되며 둘 다 같은 model·service·database 경계를 사용합니다.

웹과 터미널: run.py와 bl_cli.py는 서로 다른 실행 입구이지만 create_app(), SQLAlchemy model, BorrowRequest service를 공유합니다. 즉 different entry points · same application factory입니다.

Context의 정확한 의미: 공유하는 것은 하나의 살아 있는 웹 context가 아니라 create_app()이라는 앱 조립 규칙입니다. HTTP 요청은 Flask가 request/application context를 요청 단위로 만들고 정리하며, BL-CLI는 명령을 실행할 때만 with app.app_context():로 짧은 application context를 직접 엽니다. 따라서 context를 전역으로 오래 공유하지 않고, 같은 factory·extension·model 경계만 재사용합니다.

1.2 · Main ↔ Rose LAN Access

Main Chromebook의 Crostini에서 실행한 BookLoop를 같은 내부 네트워크의 Rose에서 검수하는 개발 운영 경계입니다. 현재 run.py의 기본값은 0.0.0.0:5000 bind와 debug=False이며, ChromeOS TCP 5000 포트 포워딩을 통해 Rose 요청이 Flask까지 전달됩니다.

Fig 1.2-1 · Main Crostini → Rose 브라우저 연결 흐름

🐍 Flask BookLoop → Crostini 0.0.0.0:5000 → ChromeOS TCP 5000 forwarding → MAIN_LAN_IP:5000 → 🖥️ Rose browser

♻️ Chromebook 재부팅 주의: Main 또는 Rose를 재부팅하면 DHCP 때문에 LAN 주소가 달라질 수 있고, ChromeOS Linux TCP 5000 포트 포워딩이 Disabled/OFF 상태로 초기화될 수 있습니다. Rose 검수 전에는 Main의 현재 Wi-Fi LAN IP와 포트 포워딩의 ON 상태를 다시 확인합니다.

외부 수동 검수: /dev/db/는 관계와 안전한 표시 필드를 확인하고, bl-cli는 명시적인 seed/reset을 실행합니다. 전체 raw SQLite schema와 row를 교차 확인할 때는 sqlite3 CLI 또는 DB Browser for SQLite로 로컬 instance/bookloop.db를 read-only 열 수 있습니다. 이런 외부 도구는 BookLoop runtime이나 제품 Admin UI가 아닙니다.

'자동화 검증 중심'이란 BorrowRequest API가 미완성이라는 의미가 결코 아닙니다. api.py의 모든 JSON API 엔드포인트는 services/borrow_requests.py의 *_service() 함수들과 100% 결합되어 있으며, pytest 스위트(124/124 tests passed)가 HTTP Test Client로 완전 검증을 마쳤습니다.

💡 api.py의 핵심 정체성과 3대 실행 파이프라인

"지금 api.py는 pytest로 검증 중인 JSON API이자, 나중에 React가 그대로 사용할 backend 입구입니다."
1. 현재 제품 UI (Jinja) Browser ➔ Jinja route ➔ Shared Service ➔ DB ➔ render_template() ➔ HTML

3. 미래 React SPA 파이프라인 React ➔ fetch() ➔ api.py ➔ 같은 Shared Service ➔ DB ➔ jsonify() ➔ JSON

🌟 Shared-Service Architecture의 대표적 깃발 (BorrowRequest)
현재 BookListing CRUD는 라우트 직접 처리(api.py ➔ validation ➔ db.session ➔ DB) 형태이지만, BorrowRequest는 api.py ➔ Shared Service (borrow_requests.py) ➔ DB로 완벽히 분리된 진정한 Shared-Service 구조를 증명하고 있습니다.
